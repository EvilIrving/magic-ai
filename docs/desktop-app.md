# 桌面端形态（规划中，未做）

> **状态：未实现。** 当前只有 CLI 引擎，没有 TUI，也没有桌面端。
> 本文记录：形态选择、Tauri 的取舍、Go 核心 / 壳层边界、以及「像桌面端软件」的验收标准。
> 前置：`README.md` / `AGENTS.md` 已把「**自有** menubar/tray + 全局热键命令面板」列为 1.0.0 之后的延期 UX（且明确不绑 Raycast/Alfred）。桌面端是这条线的延续。

---

## 1. 前提

- 桌面端**不是新引擎**，是同一个 Go 引擎的另一个前端。所有能力仍由 Go 实现。
- CLI 与 agent 调用是主入口；桌面端是并列前端，不是替代品。
- 延期决策，不阻塞 CLI。

---

## 2. 为什么排除 Electron

自带完整浏览器内核的方案（Electron / CEF / NW.js）一律不考虑：

- 单 app 打包 100–250 MB，空载 RSS 数百 MB；
- 本项目 Go 二进制只有几 MB，用户装它就是为了少配置、轻量；
- 为它塞一个浏览器内核，与产品定位直接冲突。

---

## 3. 方案对比

> 用户说的「塔 UI」= **Tauri**。但「Tauri 也许是唯一选择」这个前提**需要修正**：对一个 Go 项目，还有一个更对口的选项。

| 方案 | 内核 / 渲染 | 后端语言 | 体积 | 与本项目匹配度 |
|---|---|---|---|---|
| **Tauri 2**（当前稳定 2.11.x） | 系统 webview（macOS WKWebView / Windows WebView2 / Linux WebKitGTK） | **Rust**（Go 只能当 sidecar 子进程） | 小 | 中：要多维护一套 Rust |
| **Wails**（v2 稳定，v3 仍在 beta） | 系统 webview | **Go**（自动生成 Go↔JS 绑定） | 小 | **高：无需引入 Rust** |
| webview_go / Neutralino | 系统 webview | 任意（IPC 接后端） | 很小 | 中：更薄，能力也更少，适合纯壳 |
| 原生 SwiftUI + WinUI | 系统原生控件 | Swift / C# | 中 | 外观最像，但两套代码，成本最高 |
| Fyne / Gio | 纯 Go **自绘** | Go | 中 | 低：不是系统原生控件，不满足「像桌面端软件」 |

结论：**主要候选是 Tauri 与 Wails**。只有确定愿意额外维护一套 Rust 桥接层时，「Tauri 是唯一选择」才成立；若只想让 Go 核心直接对话前端，**Wails 更对口**。选之前先做 spike，不要直接押。

---

## 4. Tauri 的具体缺陷

用户提到的「很多交互能力不存在」，展开就是：

- **前端没有 Node API**：文件、进程、通知、托盘、对话框都要走 Rust command 或官方插件，不能在 JS 里随手做。
- **Rust 成为第二语言 + 第二套构建/签名/发布链路**。
- **系统 webview 不一致**：WKWebView / WebView2 / WebKitGTK 在 CSS、JS、字体、滚动、`localStorage` 行为上有差异，必须多端实测，不能只在 Safari 里调好就发。
- **Go 与 Rust 之间**只能：sidecar（子进程 + IPC）或 cgo（编译复杂、交叉编译困难）。两条都不便宜。

---

## 5. 架构原则（已定）

1. **Web 前端只是壳层**：不承载业务逻辑，不直接读写配置库。
2. **所有能力在本机 Go 里实现**：继续复用 `internal/`，不 fork 第二套逻辑。
3. **桥接给前台**：壳层通过一条稳定、带版本的通道调用核心。
4. **压缩体积与占用**，并保证体验像桌面软件（见 §7）。

### 桥接方式二选一

| 方式 | 说明 | 取舍 |
|---|---|---|
| **Sidecar / 子进程** | 把现有 `magic` 二进制当子进程，UI 走 stdio JSON-RPC 或本地 socket | CLI 与桌面共用同一份引擎，**天然不分叉**；需处理进程生命周期、启动、错误、并发 |
| **进程内绑定** | Go 核心编成 `c-shared` 给 Rust/Swift 调，或用 Wails 直接链接 Go | 无 IPC，调用直接；引入 cgo、交叉编译更麻烦，容易与 CLI 行为分叉 |

**倾向 sidecar**：单一引擎，CLI 与桌面永不分叉。前提是先把机读输出做出来 —— 也就是 `magic guide` / `--json`（见 [agent-guide.md](./agent-guide.md)）。

> **复用点**：`--json` 的命令契约**同时**是桌面端的 API 契约。agent-guide 和桌面端应该一起设计，别各做一套。

## 6. 边界：什么归壳层，什么归核心

| 归 **Go 核心** | 归 **壳层** |
|---|---|
| 配置库读写、skill / MCP / API 投影、provider 切换、sync、全部业务逻辑 | 原生窗口与应用菜单、托盘、全局热键、原生文件选择器、系统通知、开机自启、自动更新、窗口位置记忆、主题跟随 |

注意 `AGENTS.md` 已定：**跟手入口必须自研**，不绑 Raycast / Alfred / tinycast。

---

## 7. 「像桌面端软件」的验收标准

- 原生窗口 chrome + macOS 应用菜单 / Windows 标题栏，**不画假标题栏**
- 键盘快捷键（Cmd/Ctrl）、右键上下文菜单、拖放、双击打开 / 文件关联
- 菜单栏图标 / 托盘常驻（对应已延期的跟手入口）
- 主题跟随系统（明暗），尊重「减弱动态效果」
- 窗口大小 / 位置记忆，位置不对不改；单实例（重复启动聚焦已有窗口）
- 系统通知；可选 Dock / 任务栏角标
- **原生**文件选择器，不用自绘
- 自动更新（依赖已签名发行物 → 见 [release-signing.md](./release-signing.md)）
- 中文 IME、无障碍、拼写检查
- 首屏不用 loading 转圈当主体验；本地操作要有即时感

「压缩性能与占用」要变成可验收的数字才有意义。以下是**建议目标，待定**：

| 指标 | 建议目标 |
|---|---|
| 安装包 | < 20 MB |
| 冷启动 | < 300 ms |
| 空载常驻内存 | < 100 MB |
| 硬性约束 | 不把 Chromium / Node 打进包 |
